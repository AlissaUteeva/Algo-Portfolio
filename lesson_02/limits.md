## 1. Заказы за сутки, `n ≤ 200 000`

Есть ли среди номеров хотя бы два одинаковых?

- **Проходит:** O(n) по времени и O(n) по памяти.
- **Решение:** Идём по списку номеров один раз и складываем встреченные номера в хэш-таблицу (set). Если номер уже есть в множестве — значит, нашли дубликат.
Что мешало проще: Если делать двумя вложенными циклами, получится O(n²), а это слишком медленно для таких ограничений.
- **Что мешало проще:** Обычный перебор двумя вложенными циклами имеет сложность O(n^2), что слишком медленно для таких ограничений
- **Почему это верно (с числом):** При n = 200 000 наивный перебор занял бы (200 000)² / 2 = 2 · 10¹⁰ операций, а это превышает лимит в 10⁷ операций в секунду в 2000 раз. С хэш-таблицей будет всего около 200 000 операций — это укладывается в 0.02 секунды.

## 2. Цены на складе, `n ≤ 100 000`

Найти три самые дешёвые позиции.

- **Проходит:** O(n) по времени и O(1) по дополнительной памяти.
- **Решение:** Проходим по массиву один раз и поддерживаем три минимальных значения в отдельных переменных.
- **Что мешало проще:** Полная сортировка массива O(n log n) работает дольше и делает лишнюю работу, хотя для n = 100 000 она бы тоже уложилась в лимит.
- **Почему это верно (с числом):** При n = 100 000 поиск трёх минимумов за один проход займёт ровно 100 000 итераций. Это всего 1% от секундного лимита в 10⁷ операций — очень мало.

## 3. Архив чеков `n ≤ 10⁷`, запросов `q ≤ 10⁵`

Отсортирован. По каждому запросу сказать, есть ли такой чек.

- **Проходит:** O(q log n) по времени.
- **Решение:** Для каждого из q запросов запускаем бинарный поиск по уже отсортированному массиву чеков.
- **Что мешало проще:** Если делать линейный поиск O(n) на каждый запрос, общая сложность станет O(q · n), а это вообще неприемлемо.
- **Почему это верно (с числом):** Линейный поиск потребовал бы q · n = 10⁵ · 10⁷ = 10¹² операций. Бинарный поиск на один запрос делает log₂(10⁷) ≈ 24 операции. На все запросы выйдет 10⁵ · 24 = 2.4 · 10⁶ операций — заметно меньше порога в 10⁷.

## 4. Координаты курьеров, `n ≤ 3 000`

Найти двух ближайших друг к другу.

- **Проходит:** O(n²) по времени.
- **Решение:** Полный перебор всех пар курьеров двумя вложенными циклами с вычислением расстояния между ними.
- **Что мешало проще:** Есть более сложные алгоритмы (например, «разделяй и властвуй» за O(n log n)), но писать их избыточно, потому что n достаточно маленькое.
- **Почему это верно (с числом):** Для n = 3 000 количество пар в переборе — n · (n − 1) / 2 = 3000 · 2999 / 2 ≈ 4.5 · 10⁶ операций. Это меньше 10⁷, поэтому обычный перебор точно уложится в секунду.

## 5. Одно число `k ≤ 10⁹`

Сколько раз его можно разделить пополам до единицы?

- **Проходит:** O(log k) по времени.
- **Решение:** Обычный цикл while k > 1: k //= 2 со счётчиком шагов, либо вычисление двоичного логарифма.
- **Что мешало проще:** Число k большое, но деление пополам уменьшает его очень быстро, так что усложнять смысла нет.
- **Почему это верно (с числом):** Даже для максимального k = 10⁹ цикл выполнится всего log₂(10⁹) ≈ 30 раз.

## 6. Две накладные, `n ≤ 10⁵` и `m ≤ 10⁵`

Обе отсортированы. Собрать из них один отсортированный список.

- **Проходит:** O(n + m) по времени.
- **Решение:** Используем два указателя. Сравниваем текущие элементы в обеих накладных и продвигаем тот указатель, где элемент меньше, по очереди добавляя элементы в новый список.
- **Что мешало проще:** Слить списки через .extend() и потом сделать общий sort() — это O((n+m) log(n+m)), что хуже линейного слияния.
- **Почему это верно (с числом):** Алгоритм двух указателей сделает ровно n + m шагов. При n = 10⁵ и m = 10⁵ это 10⁵ + 10⁵ = 2 · 10⁵ операций — в 50 раз меньше порога в 10⁷ операций в секунду.

## 7. Где модель ошиблась

Одно место, где модель ответила неверно или расплывчато, и как вы это
заметили.
